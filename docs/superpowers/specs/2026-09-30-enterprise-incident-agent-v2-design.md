# 企业级故障响应 Agent V2 设计规格

日期：2026-09-30  
状态：待实施  
目标仓库：`ailab-ops-copilot`

## 1. 背景与目标

现有项目已经具备故障数据、只读工具、检索、评测、并发保护和可观测性等工程资产，但默认路径的核心判断由 `faults.yaml`、`signals.py` 和确定性 `MockLLMClient` 完成。它适合展示规则诊断系统，却不能清楚呈现现代 Agent 中“大模型负责判断、确定性系统负责约束”的职责边界。现有六份 PDF 只有 6–8 页，内容形态接近逐字讲稿，也不适合作为可独立阅读的项目教材。

本次在原仓库内进行第二代重构，不受现有模块兼容性的限制。Git 历史保留，旧版本可追溯；有价值的领域素材和工程实现可以选择性复用。

目标读者统一假设为：具备 Python 基础，但没有 LLM、RAG 或 Agent 项目经验。课堂不现场编写代码，教师带领学生阅读知识型 PDF、讲解架构、阅读关键代码并运行演示；学生课后自行复习和模仿。

项目目标：

- 构建一个以真实大模型为主路径的企业级 AI 训练任务故障响应 Agent。
- 用一个连续项目讲清 LLM、工具调用、Agent 控制、RAG、证据链、安全、评测和生产化。
- 默认支持 OpenAI 兼容 API，同时提供诚实、明确标注的离线案例回放。
- 让每个关键结论均可追溯到真实工具结果，让所有有副作用的动作均经过审批。
- 产出六份知识型 PDF 和一份合订本，内容由知识密度决定，不人为凑课时。

## 2. 非目标

- 不追求展示尽可能多的 Agent 框架或供应商 SDK。
- 不把多 Agent 当作默认架构；只有职责隔离确有价值时才增加审查角色。
- 不要求学生在课堂完成编码实验。
- 不通过提示词代替权限、安全或证据校验。
- 不用规则推理器伪装成离线大模型。
- 不承诺对真实生产平台执行写操作；教学环境中的动作均为模拟执行。
- 不为兼容旧项目内部实现而保留不合理边界。

## 3. 产品定位

用户提供 job ID 或故障描述，Agent 自主选择只读工具读取任务、日志、指标、节点与历史事件，检索企业 Runbook，维护候选根因和证据链，并输出带引用、置信度、未知项和修复方案的调查报告。

当用户要求采取行动时，系统只生成行动计划。重启任务、修改资源或隔离节点等动作必须经过人工审批，并在教学环境中模拟执行、留下审计记录。

核心设计原则是：

> 大模型负责计划、工具选择、提出和修正假设、组织报告；确定性代码负责状态、权限、证据存在性、预算、审批和审计。

## 4. 系统架构

```text
用户 / Web UI / CLI
        │
        ▼
任务会话与调查状态
        │
        ▼
Agent Orchestrator
  ├─ 调查计划
  ├─ 工具选择
  ├─ 候选假设
  ├─ 证据校验
  └─ 报告生成
        │
        ├──────────────┐
        ▼              ▼
只读调查工具          企业知识库
任务 / 日志 / 指标    Runbook / 历史事件
节点 / 事件           检索 / 引用
        │              │
        └──────┬───────┘
               ▼
          Evidence Store
       事实、来源、时间、可信度
               │
               ▼
       Policy & Approval Gate
       只读自动执行 / 写操作审批
               │
               ▼
       诊断报告 / 修复计划 / Trace
```

### 4.1 `agent/`

使用显式调查状态机组织一次调查。主要阶段为：理解问题、收集基础事实、形成候选假设、补充调查、验证结论、生成报告。每个阶段有清晰输入、输出、预算和停止条件。

系统不以固定流水线代替 Agent。状态机限定合法行为和终止条件，具体调用什么工具、先验证哪个假设仍由模型依据上下文决定。

### 4.2 `tools/`

工具分为两类：

- 只读调查工具：读取任务、日志、指标、节点、事件、历史事故和 Runbook，可在策略允许时自动执行。
- 动作工具：重启、修改资源、隔离节点等，只能创建待审批动作；审批通过后也只在教学世界中模拟执行。

工具具有结构化输入输出、超时、数据量上限、敏感字段标记、幂等说明和权限声明。

### 4.3 `evidence/`

证据不等同于任意工具输出。标准证据对象至少包含：

- 唯一 ID 与事实摘要
- 来源工具及调用参数
- 时间范围和原始摘录
- 完整性与截断状态
- 支持、反驳或关联的候选假设
- 可用于报告引用的稳定定位信息

最终报告中的关键主张必须引用 Evidence Store 中存在的证据。系统检查引用存在性和主张—证据关联，但不替模型选择根因。

### 4.4 `knowledge/`

Runbook、历史事件和平台说明是 Agent 可见知识。评测标签是不可见资产，两者独立维护。知识库不得与评测答案从同一份真相文件派生。

检索支持词法、向量和混合策略。查询在读取具体信号后构造，避免直接使用“为什么失败了”这类无信息问题检索。

### 4.5 `models/`

真实 OpenAI 兼容接口是主路径，统一处理结构化输出、工具调用、连接/读取超时、有限重试、上下文预算、token 与成本统计。

离线模式由固定案例和预录模型响应驱动，用于无 API Key 时浏览流程、运行 UI 和复现教材案例。离线模式必须在界面、日志和文档中明确标注为回放，不对未录制输入伪造智能回答。

### 4.6 `policy/` 与 `approvals/`

集中定义工具权限、自动执行条件、审批规则、敏感信息脱敏、最大步骤、最大 token、最大费用和总截止时间。提示词只说明行为期望，不承担安全强制职责。

待审批动作包含理由、参数、风险、预期影响、回滚说明和关联证据。批准、拒绝、过期和模拟执行均进入审计日志。

### 4.7 `evals/`

评测分层覆盖：

- 工具选择与参数正确性
- 必需证据覆盖率
- 证据忠实度与引用准确率
- 候选根因和最终根因判断
- 正确拒答与错误自信
- 策略违规和越权动作
- 任务完成率、token、费用和延迟

真实模型评测支持重复运行，报告均值、波动和失败类型。确定性单元测试覆盖状态机、策略、工具、引用校验和审批，不依赖真实 API。

### 4.8 `observability/`

一次调查生成完整 trace，包括模型请求、工具调用、状态迁移、候选假设变化、证据新增、token、费用、重试、审批和最终决策。

Web UI 的主要用途是解释调查过程：展示时间线、证据板、候选假设、报告和审批，而不是堆砌无关运维指标。

## 5. 核心调查流程

1. 用户输入 job ID 和调查目标。
2. 系统创建会话，载入权限、步骤、token、费用和时间预算。
3. Agent 获取任务概况并提出可更新的简短调查计划。
4. 工具结果经标准化后进入 Evidence Store，原始响应另行保留。
5. Agent 维护 2–4 个候选根因，优先寻找能区分候选项的证据。
6. Agent 基于已观察到的错误、指标形态和状态检索知识库。
7. 生成结论前，系统校验证据引用、冲突、最低证据要求和策略约束。
8. Agent 输出结构化报告：结论、置信度、时间线、证据、排除项、未知信息、修复建议与引用。
9. 用户请求修复时，系统生成待审批动作；教学环境在批准后进行模拟执行并审计。

## 6. 错误与降级处理

- 工具参数错误：返回可修正的结构化错误，允许 Agent 调整一次。
- 工具超时：按工具幂等策略有限重试，失败后标记证据缺失。
- 模型超时或限流：带抖动退避，在预算内重试；超限后保存可恢复调查状态。
- 上下文过长：压缩已确认事实和旧对话，不丢失证据索引与关键原文定位。
- 证据冲突：保留多个候选项并说明缺口，不强行得出唯一根因。
- 引用不存在：阻止报告发布，要求模型基于现有证据重新生成。
- 模型不可用：已有在线调查进入可恢复状态；用户可以进入明确标注的离线回放。
- 写操作未批准：拒绝执行但保留行动计划；审批过期后需要重新申请。
- 超预算：停止新模型和工具调用，输出当前事实、未知项和停止原因。

## 7. 六节课教材结构

六节课不设固定时长，由内容决定，通常以 60–90 分钟可讲清一个完整主题为尺度。课堂以教师带读、架构解释、关键代码阅读和运行演示为主，不安排现场编码实验。

### 第 1 课：从 LLM 到 Agent

讲清 LLM、消息、上下文、结构化输出、工具调用和最小 Agent Loop。以人工排障和 Agent 排障的对照建立直觉，并阅读项目中最短的一条完整调用链。

### 第 2 课：让调查过程可控

讲调查状态机、动态计划、步数与时间预算、停止条件、工具错误回喂、幂等和上下文管理。通过重复调用、编造参数和无法停止等失败案例解释控制层。

### 第 3 课：RAG、证据链与可信回答

讲切分、词法、向量、混合检索、重排和引用。重点说明观察后检索、证据对象和主张—证据关联。重建并保留“错误融合可能拉低检索效果”的实验。

### 第 4 课：安全边界与人工审批

讲只读与动作工具、最小权限、审批门、脱敏、审计和提示注入。用“可以建议重启，但不能自行重启”展示企业 Agent 的边界。

### 第 5 课：如何评测一个 Agent

讲工具、参数、证据、引用、结论、拒答、策略、成本和延迟的分层指标；讲独立评测集、重复运行、波动和失败归因，并解释闭环 100% 的局限。

### 第 6 课：从 Demo 到企业级服务

讲 API、流式响应、并发闸门、限流、重试、熔断、缓存、降级、trace 和部署边界。以一次完整调查、一次模型故障、一次审批和一次评测回归收束项目。

## 8. PDF 与教材产物

PDF 是书本式项目阅读材料，不是幻灯片，也不是逐字讲稿。采用 A4 版式，适合课堂带读和课后连续阅读。

每课固定组织为：

1. 本章解决的问题
2. 贯穿本章的故障案例
3. 概念与直觉
4. 项目架构中的对应位置
5. 流程图或时序图
6. 精选代码片段与解释
7. 常见错误与反例
8. 真实运行结果或实验数据
9. 本章总结
10. 课后阅读、模仿方向与思考题

版式要求：

- 正文具有书籍式连续叙事和清晰层级。
- 使用架构图、流程图、时序图、表格、代码框、术语框、警告框和旁注。
- PDF 中只放值得讲解的代码片段，完整代码以仓库为准并注明路径。
- 图、实验数字和截图必须由当前代码或可追溯素材生成。
- 中文字体嵌入 PDF，文本可复制和搜索。
- 每课预计 15–25 页，但不以页数或课时为硬指标。

最终产物包括六份分课 PDF、一份合订版 PDF、可维护的教材源文件、图表与实验资产，以及独立的教师带读提示。

## 9. 现有资产处置原则

### 优先保留或改造

- 故障场景中的领域知识与具有代表性的日志、指标素材
- 只读工具的业务含义和部分接口测试
- 并发闸门、限流、熔断与 trace 中已被测试验证的工程思想
- 检索对比实验中“弱检索器会拖累融合”的教学发现
- 中文字体与可复现 PDF 构建的基本要求

### 重新设计

- Agent 状态与控制流程
- LLM 接口与真实 API 主路径
- 数据、知识库和评测集的边界
- Web UI 的信息架构
- 评测指标和报告
- 课程内容、图表、讲师提示和 PDF 排版系统

### 移除或降级为基线实验

- `MockLLMClient` 作为默认推理核心的定位
- `signals.py` 直接裁决最终根因的主路径
- 从同一份 `faults.yaml` 同时派生知识、推理与评测答案的闭环
- 以逐字稿为主体的现有六课内容
- 为兼容旧内部实现而存在、但不再服务新架构的模块

删除动作必须在实施计划中列出具体文件，并在对应替代物和测试存在后执行。

## 10. 测试与验收

### 项目验收

- 配置真实 OpenAI 兼容 API 后，可以完成端到端故障调查。
- 没有 API Key 时，可以启动并运行明确标注的离线案例回放。
- 每个报告关键主张均引用实际存在的证据。
- 未审批的动作不会执行，批准和拒绝都有审计记录。
- 单元测试不访问外网，关键状态机、策略和审批路径均被覆盖。
- 至少一个独立评测集不由知识库或规则配置自动派生。
- Web UI 能清楚展示调查时间线、证据、假设变化、报告和审批状态。

### 教材验收

- 六课均能脱离课堂独立阅读，不依赖逐字讲稿才能理解。
- 代码路径、命令、截图和实验数字与当前仓库一致。
- 六份分课 PDF 和合订本均可重复生成。
- 随机抽查首页、目录、正文、代码、图表和跨页表格，无溢出、孤行或不可读字号。
- PDF 中文字体已嵌入，文字可复制、可搜索。
- 教师提示与学生正文分离。

## 11. 实施边界与顺序

这是一个仓库级重构，但按可验证的纵向切片推进：

1. 固化新领域模型、证据模型和独立案例资产。
2. 建立真实模型接口、调查状态机和最小端到端路径。
3. 加入检索、引用校验、策略和审批。
4. 建立离线回放、评测和可观测性。
5. 重做 Web UI 与生产保护层。
6. 在代码和实验稳定后编写六课教材并生成 PDF。

教材最后完成，但从第一阶段开始同步记录架构决策、反例、实验和图表数据，避免教材成为事后编造的说明。
